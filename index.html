Abstract

Measured on real bug fixes, against a pinned competitor

CodeBuddy is a local context and memory layer. It attaches to the agent through lifecycle hooks and a lean Model Context Protocol profile, stays out of the model request path, and keeps its index and memory on the developer's machine.

On 23 merged Litestar bug fixes run as 138 Claude Code sessions, CodeBuddy 2.16 removed 79% of tool-output tokens on a 20-command corpus (Headroom 0.44: 55%), processed 10.0% fewer tokens than stock Claude Code, spent 4.4% less in total ($5.28 vs. $5.53; the paired median cost per task was slightly higher than stock, not significantly), and recalled 12/12 stored project conventions from a fresh process.

In the earlier 2.15.3 study of 117 sessions, agents with CodeBuddy answered 15/15 questions on unwritten team rules, matching a hand-written notes file holding all 220 notes at 27% lower cost per question (a no-information control answered 0/15). Context packs were 62–90% smaller than the files they replaced.

1 · Introduction

Every agent session pays a context tax

Coding agents such as Claude Code, Codex and OpenCode now search repositories, read files, run tests and write patches. Each step has a price in context. A verbose test log or a whole-file read enters the conversation and is re-sent on every later turn; every exposed tool schema is paid for on every request; and long contexts are used less reliably than short ones. Each new session also starts empty, so a team's unwritten rules are rediscovered at cost, pasted wholesale into an instructions file, or lost.

P1 · Token volume

Whole files, whole logs

Agents take in whole files and whole command outputs when only a fraction is relevant.

P2 · Context selection

A few files among thousands

The agent must find the few relevant files, and should hear nothing when the evidence is weak.

P3 · Project memory

Rules nobody wrote down

Decisions and conventions must reach the agent when they apply, without injecting every note into every session.

CodeBuddy addresses all three in one local layer that runs beside the agent, not between the agent and the model provider. Hooks deliver ranked file pointers and recalled facts, a reducer shortens noisy command output while keeping the full text recoverable, and a reviewed project memory carries decisions across sessions.

The program moved fast and stayed measured. The first commit landed on 18 June 2026; by 17 November the project had 459 commits and 26 releases from 2.0.0 to 2.16.0, 20 of them between 1 and 17 November. Ten research loops ran between 13 and 18 November, and the gaps they found were ranked into fixes that shipped within days.

2 · Background and related work

Where CodeBuddy sits among context tools

Retrieval for code

Repository-level retrieval improves completion, and agentless pipelines show that explicit localisation competes with free-form exploration. Agentic-search comparisons depend strongly on the harness, so both studies hold agent, model, prompt and permissions fixed across arms.

Context compression

Prompt compression learns which tokens to drop. Headroom takes the proxy route and compresses requests on the way out; RTK filters shell output through a hook. CodeBuddy decides which project evidence enters the context at all, from inside the agent loop.

Code intelligence

Serena exposes symbol-level tools, codebase-memory-mcp serves a code knowledge graph, and context-mode sandboxes tool output. The 2.15.3 paper compared CodeBuddy with all five of these tools in their default setups.

Agent memory

MemGPT, Mem0, Zep and LongMemEval study memory hierarchies, extraction and temporally valid facts. CodeBuddy targets repository-scoped engineering memory: facts tied to a codebase and its team, reviewed before storage and delivered with date and source.

3 · How we planned it

No claim without a benchmark, no gap without a ranked fix

Each loop starts from a sceptical research handoff, fixes its measurement in writing before any paid run, benchmarks on the public Litestar repository, ranks the gaps by expected effect and effort, and ships the top fixes. The release is re-benchmarked, and the result seeds the next handoff.

Case study: two turns of the loop

2.9 → 2.10. A project-reported agent A/B on 23 Litestar fixes, which we did not independently reproduce, found that CodeBuddy 2.9 cost a median 22% more per task than stock Claude Code, with an unchanged pass rate, and that the agent made 0 calls to CodeBuddy's tools. The cost was the fixed per-session prefix. Version 2.10 cut the default tool schemas from 3,486 to 253 tokens (schema counts vary slightly by release, profile and counting method: 294 and 3,934 in the 2.15.3 paper, 253 and 3,463 in the 2.16 report) and the managed rules from 761 to 144 tokens.

2.15.3 → 2.16. The five-tool comparison found that setup rules and hooks disagreed (memory cost $0.0233 per question against $0.0199 for Headroom in token mode) and that output reduction was opt-in. An improvement plan ranked seven fixes. CodeBuddy 2.16.0 shipped two days later, and the 2.16 head-to-head measured a 79% output cut on the command corpus and 4.4% lower total spend than stock.

4 · System overview

Three capabilities, one local store, six lifecycles

We describe CodeBuddy as a black box: what each capability does, when it runs and what it delivers. The context layer ranks the files a prompt is likely about and delivers short pointers. Project memory holds reviewed team facts and recalls the ones that apply. The output reducer shortens noisy command output and keeps the original. The agent reaches them through hooks and an optional MCP server whose lean default profile costs 253 schema tokens.

Bound everything

Every payload has a budget.

Never destroy information

Every reduction is recoverable.

Prefer silence to noise

Nothing is delivered when evidence is weak. Every item shows its provenance, and memories show when they were recorded.

6 · Evaluation methodology

Two controlled studies on one public repository

Both studies run on Litestar, an actively maintained open-source Python ASGI framework, and hold the agent, model, prompt and tool permissions fixed across arms, so the only difference is the tool under test.

7 · Results I: the 2.15.3 program

Team memory that matches a full notes file, at lower cost

What 2.15.3 established

With CodeBuddy, agents answered 15/15 questions on unwritten team rules, matching a hand-written notes file holding all 220 notes at 27% lower cost per question; a no-information control answered 0/15. Context packs were 62–90% smaller than the files they replaced, command output fell by 92% and oversized first reads by 93%, and keyword recall ranked the right fact first in 20/20 queries at both 20 and 220 stored facts. In the five-tool comparison, CodeBuddy had the lowest cost per correct answer among the five arms that ran both task types (four tool configurations and no tool; $0.0507, 49/51 correct).

Two results were not yet wins, and both fed the 2.16 plan: in the three-arm paired agent study (36 code-search sessions per arm), short code search cost 18% more than no tool (95% CI +5% to +35%; the separate five-tool comparison measured +3%), and on a 20-task SWE-bench Verified pilot CodeBuddy solved 13/20 against 14/20 for the stock agent.

Project memory. The stock agent searched for 4.6 turns on average and answered 0/15. With CodeBuddy the prompt hook recalled the right note and the agent answered 15/15 in 1.2 turns, at $0.0227 per question. A notes file holding all 220 notes also answered 15/15 and was faster (4.8 s against 7.7 s), but cost $0.0310 per question, because it writes every note to the prompt cache in each session.

Recall at scale. An 11-fold increase in stored notes left first-rank keyword recall unchanged at 20/20, with p95 latency at or below 25 ms. Reworded recall was lower and declined with scale (top-3: 17/20 at 20 facts, 15/20 at 220). At 220 notes one recall cost 682 tokens against 5,422 for loading the notes file.

Where cost did not yet fall. In the 36 paired code-search sessions of the three-arm agent study, CodeBuddy used 10% fewer input tokens and 8% fewer turns at equal accuracy (33/36 in both arms), but cost 18% more. The cause was prompt-cache pricing: hints were new text in each session and were written to the cache at a premium, while the tokens they saved were mostly cheap cache reads. On the SWE-bench pilot CodeBuddy cost $2.16 against $1.83 (+17.7%, 95% CI −1.7% to +36.9%). Both became 2.16 fixes: cache-stable delivery and background indexing.

File retrieval. On tasks phrased in the code's own words, CodeBuddy ranked a correct file first in 83% of tasks while returning about 3 files, where a package-level keyword ranker returned about 140. Reworded tasks remained hard (top-1 30%, top-3 50%).

8 · Results II: the 2.16 head-to-head

Lowest total bill, largest output cut, and four measures where Headroom led

23 merged Litestar bug fixes, 138 sessions, 46 task-runs per arm, summarised from the companion technical report. The diamond marks the best value in each row, whichever arm holds it.

Pass rate. Pass rates were Headroom 61% (28/46); CodeBuddy and stock 57% (26/46 each). Exact McNemar gives p = 1.00 for CodeBuddy and p = 0.50 for Headroom against stock: neither difference is significant. Passing more fixes at a similar total gave Headroom the lowest cost per passing fix, $0.196 against $0.203 for CodeBuddy and $0.213 for stock.

The reducer has not yet reached sessions. In the benchmarked 2.16.0 sessions the automatic reducer did not fire: it was used in 0 of 46 CodeBuddy runs, and neither tool's MCP server was called. The 79% corpus cut is a measured capability; the session-level token savings came from the other delivery paths. Confirming automatic routing end to end is frontier item 1.

Context. Median peak context was 35.7k tokens for CodeBuddy and stock and 35.3k for Headroom. Headroom's paired reduction of 714 tokens (pHolm = 0.01) is the one secondary metric in either arm that is significant after correction.

Footprint: where Headroom leads most clearly

Headroom runs as a local HTTP proxy and used a median 178 MB during sessions. CodeBuddy runs alongside PostgreSQL with pgvector, which holds its index and memory; its processes used a median 1,292 MB during sessions and 2,104 MB while indexing. The larger cost is per repository: the first index of Litestar took a median 494 s and 8,736 MB of disk, where Headroom builds no index. That index is what makes ranked pointers and recall possible; its size and build time are now research targets.

10 · Discussion

Why it matters

Economics at fleet scale

Scaling each arm's mean cost per task-run to 1,000 similar tasks gives $115 for CodeBuddy, $119 for Headroom and $120 for stock. This is an extrapolation from 46 task-runs on one repository, not a measurement: the means favour CodeBuddy, the paired medians do not, and the difference is not significant. It shows the shape of the opportunity. Most of each session's tokens are context re-sent from turn to turn (for stock, cache reads were a median 157,892 of 170,127 tokens per task), so what enters early is paid for again on every later turn.

Memory is a core strength

Memory is where results are most consistent across both studies: parity with a full notes file at 27% lower cost per question, and 12/12 conventions recalled at 146 tokens against 9,689 to re-derive them. It is not uncontested: in 2.15.3 Headroom in token mode also answered 15/15 and was cheaper per question ($0.0199 against $0.0233), and Headroom's memory was not measured in 2.16.

Complementary, not only competing

Headroom compresses requests in the request path; CodeBuddy decides what enters the context from inside the agent loop. Each led on different measures here. Whether the two combine well was not measured, and it is a natural follow-up.

A team that measures, then ships

Two days passed between the 2.15.3 benchmark and 2.16.0, and the 2.16 benchmark then checked the result against a pinned competitor. Every gap is carried forward with its number. The record of measured claims, including the ones that went against us, is the strongest evidence we can offer.

11 · The research frontier

Every measured weakness is a numbered target

Each target will be re-measured on the same harness before any gain is claimed. The first and third matter most for cost and adoption: if automatic reduction reaches sessions at anything like its corpus rate, the largest measured saving becomes a per-session one, and a smaller footprint removes the main practical reason to choose a lighter tool. The fourth is central to trust: a memory layer has to forget what its users have corrected.

12 · Conclusion

Strengths confirmed twice, gaps carried forward with numbers

In five months CodeBuddy grew from a memory server into a local context and memory layer with 26 releases, 4,966 npm downloads and two controlled studies on a production codebase. The studies agree on its strengths: project memory that matches a full notes file at lower cost and recalls stored conventions across sessions (15/15; 12/12), context and command output cut by large margins at the call level (62–90%; 79% on the 2.16 corpus), the lowest cost per correct answer among the five 2.15.3 arms that ran both task types, and the lowest total bill of three arms in 2.16.

They also agree on what is not yet done: Headroom passed two more fixes and used far less memory, per-task cost differences are not significant at this sample size, and the reducer has yet to reach real sessions. Each of those is now a numbered target. The method that produced 2.16 two days after the gaps were measured is the same one that will test whether they close.
